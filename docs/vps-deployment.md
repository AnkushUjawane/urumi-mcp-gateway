# Production-like deployment (VPS, k3s) and upgrades

**Status: `<EDIT: "deployed and verified on <provider>, <domain>" OR "values prepared, not deployed on a VPS">`.**

## What changes between local and VPS (Helm values only)

| Setting | Local | VPS | Where |
|---|---|---|---|
| Hosts | `shop.localtest.me`, `app.localtest.me` | `shop.<domain>`, `app.<domain>` | `store` and `platform` `values-prod.yaml` (`ingress.host`) |
| Scheme | `http` | `https` | `store` `scheme` (sets WordPress `WP_HOME`) |
| TLS | none | cert-manager ClusterIssuer `letsencrypt-prod` | `ingress.tls.*` |
| Cookies | `COOKIE_SECURE=false` | `true` | `platform` `gateway.cookieSecure` |
| Storage | `local-path` default | `local-path` and larger sizes | `persistence.*` |
| Secrets | generated by charts | created beforehand: `existingSecret` | `store-secrets-prod`, `platform-secrets-prod` |
| Images | `urumi-registry:5000/...` | a pullable registry | `*.image.repository` |

## Steps

1. VPS: Ubuntu, 2 vCPU / 4 GB RAM or more; open 22, 80, 443 only (keep 6443 closed). DNS A records for `shop.<domain>` and `app.<domain>` pointing at the VPS (use subdomains; do not touch the apex).
2. Install k3s (`curl -sfL https://get.k3s.io | sh -`). Traefik, local-path storage and the NetworkPolicy controller come with it.
3. Install cert-manager and create a `letsencrypt-prod` ClusterIssuer (HTTP-01 through Traefik).
4. Push images to a registry and set `repository`/`tag` in the three `values-prod.yaml` files.
5. Create Secrets (not in git):
   - `store-secrets-prod` in `store`: keys `db-password`, `db-root-password`, `wp-admin-password`, `woo-consumer-key` (`ck_` + 40 chars), `woo-consumer-secret` (`cs_` + 40 chars).
   - `platform-secrets-prod` in `platform`: keys `postgres-password`, `encryption-key` (32+ chars), `session-secret` (32+ chars), `admin-password`.
   - `llm-secrets` in `platform`: run `scripts/set-llm-keys.sh`.
6. Install:

       helm upgrade --install store charts/store -n store --create-namespace -f charts/store/values-prod.yaml
       helm upgrade --install mcp-servers charts/mcp-servers -n mcp --create-namespace -f charts/mcp-servers/values-prod.yaml
       helm upgrade --install platform charts/platform -n platform --create-namespace -f charts/platform/values-prod.yaml

7. Update `gateway.seedWooUrl` if needed, log in, and register `notes` and `utils` as in the README.

`<VERIFY before claiming anything: every value above was written from the local setup and has not been run on a VPS unless you did so.>`

## Upgrade and rollback with Helm

Each release is versioned. Images carry unique tags (`scripts/deploy-gateway.sh`, `scripts/deploy-dashboard.sh`), so a rollout is a new ReplicaSet and a rollback is the previous one.

    helm history platform -n platform                 # list revisions
    ./scripts/deploy-gateway.sh                        # upgrade: build, push unique tag, helm upgrade
    kubectl rollout status deploy/gateway -n platform
    helm rollback platform <REVISION> -n platform --wait   # roll back to a known-good revision
    kubectl get deploy gateway -n platform -o jsonpath='{.spec.template.spec.containers[0].image}'

What makes rollback safe here:
- Data lives in PVCs and Secrets annotated `helm.sh/resource-policy: keep`; they survive upgrades, rollbacks and uninstalls.
- Secrets use `lookup`, so upgrades never regenerate passwords.
- Database migrations are append-only numbered SQL files run under an advisory lock; a rollback of the gateway image does not undo a migration, so migrations must stay backwards compatible (new tables and columns, no drops).
- The store chart's setup Job is idempotent and reruns on upgrade.
- Do not hand-edit Helm-owned objects (`kubectl set env` caused a failed upgrade once).

Store and MCP servers: same commands with `-n store` / `-n mcp` and their chart.
